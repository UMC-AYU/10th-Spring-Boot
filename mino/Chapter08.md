## 핵심 키워드 정리

### Spring Security가 무엇인가?

Spring Security는 Spring 기반 애플리케이션의 인증(Authentication), 인가(Authorization) 및 일반적인 보안 공격 방어를 책임지는 표준 프레임워크입니다.

**핵심 동작 원리**
Spring MVC의 `DispatcherServlet`에 요청이 도달하기 전, 서블릿 컨테이너 계층에서 `FilterChainProxy`**와 복수의 보안 필터**가 요청을 가로채어 보안 검사를 수행합니다.

**장점**

- **선언적 보안 및 비즈니스 로직 분리**: 보안 코드가 비즈니스 로직(Service, Controller)에 섞이지 않고, 설정 파일이나 어노테이션(`@PreAuthorize` 등)으로 깔끔하게 분리됩니다.
- **검증된 웹 취약점 기본 방어**: CSRF(개조 사이트 요청 위조), 세션 고정(Session Fixation), 클릭재킹(Clickjacking), XSS(크로스 사이트 스크립팅) 등 흔한 웹 보안 공격을 별도 구현 없이 설정만으로 방어합니다.
- **강력한 암호화 기본 지원**: 자체적인 `PasswordEncoder` 구조를 통해 복호화가 불가능한 고성능 단방향 해시 알고리즘인 **BCrypt**, **Argon2** 등을 기본 제공하여 안전한 비밀번호 저장을 돕습니다.
- **유연한 확장성과 표준 지원**: LDAP, OAuth2, OpenID Connect, JWT, SAML 등 기업용 및 글로벌 표준 인증 프로토콜을 모듈 형태로 쉽게 연동할 수 있습니다

**단점**

- **높은 학습 곡선과 복잡성**: 내부 아키텍처(`AuthenticationManager`, `ProviderManager`, `UserDetailsService` 등)가 매우 유기적이고 복잡하게 얽혀 있어 구조를 정확히 이해하지 못하면 커스텀 구현이 어렵습니다.
- **디버깅의 난해함**: 요청이 컨트롤러에 가기도 전에 필터 단에서 차단되거나 예외가 발생하므로, 에러 로그가 불분명할 경우 어떤 필터에서 문제가 생겼는지 추적하기 어렵습니다.
- **초기 설정의 무거움**: 간단한 토이 프로젝트나 마이크로서비스(MSA)를 만들 때도 의존성(Dependency)을 추가하는 순간 모든 API가 잠겨버리므로 기본적인 설정 비용이 발생합니다

**사용 시 유의할 점**

- **API 서버(Stateless) 개발 시 CSRF 설정 유의**: Spring Security는 기본적으로 CSRF 방어가 켜져 있습니다. 세션을 쓰지 않는 REST API(JWT 기반 환경)라면 `csrf().disable()` 처리를 해주어야 정상적인 POST/PUT 요청이 작동합니다.
- **허용 경로(PermitAll)와 무시 경로(Ignoring) 구분**
  • `HttpSecurity`에서 `.permitAll()`로 열어둔 경로는 **보안 필터를 거치되 통과**하는 것입니다 (로그인 안 한 사용자도 허용).
  • 정적 파일(CSS, JS, 이미지)은 `WebSecurityCustomizer`를 통해 필터 자체를 타지 않도록 `ignoring()` 설정을 해야 불필요한 성능 낭비를 막을 수 있습니다.
- **CORS 설정 순서**: 프론트엔드와 백엔드 도메인이 다를 때, Spring MVC의 CORS 설정보다 **Spring Security의 CORS 필터 설정이 먼저 적용**되어야 브라우저 차단 에러를 막을 수 있습니다.
- **ThreadLocal 기반 Context 관리 인지**: 인증 정보가 저장되는 `SecurityContextHolder`는 기본적으로 `ThreadLocal` 방식을 씁니다. 즉, 비동기 처리(`@Async`)나 별도 스레드를 띄워 작업할 때는 인증 정보가 공유되지 않으므로, 이에 맞는 설정(`MODE_INHERITABLETHREADLOCAL`)을 고려해야 합니다


### 인증(Authentication)vs 인가(Authorization)

**인증(Authentication)의 특징**

• **다양한 수단 제공**: ID/PW 같은 지식 기반부터, OTP 같은 소유 기반, 지문/안면인식 같은 생체 기반 인증을 조합(MFA, 다요소 인증)하여 보안을 강화할 수 있습니다.
• **세션 vs 토큰 방식**: 전통적인 웹은 서버 메모리에 신원을 기억하는 '세션' 방식을 썼으나, 최신 대규모 시스템이나 마이크로서비스(MSA) 환경에서는 신원 증명서를 암호화된 문자열로 주고받는 'JWT(JSON Web Token)' 방식을 주로 사용합니다.

**인가(Authorization)의 특징**

• **역할 기반 통제(RBAC - Role-Based Access Control)**: 가장 대중적인 방식으로, 사용자에게 'ADMIN', 'USER' 같은 역할을 부여하고 역할에 따라 접근을 제한합니다. (예: `hasRole('ADMIN')`)
• **세밀한 제어(Fine-grained Control)**: 메서드나 URL 단위뿐만 아니라, "본인이 작성한 글만 수정할 수 있다"와 같이 도메인 객체의 소유권을 검증하는 동적 인가 처리가 가능합니다.

**세부 사항 비교**

| **비교 항목** | **인증 (Authentication)** | **인가 (Authorization)** |
| --- | --- | --- |
| **목적** | 신원 확인 (Identity Verification) | 권한 부여 및 통제 (Access Control) |
| **핵심 질문** | "당신은 시스템에 등록된 그 사람이 맞습니까?" | "당신이 이 데이터(또는 기능)를 볼 자격이 있습니까?" |
| **일어나는 시점** | **항상 인가보다 먼저 실행됨** (누구인지 알아야 권한을 주므로) | 인증이 성공적으로 완료된 후 실행됨 |
| **Spring Security 구성 요소** | `AuthenticationManager`, `AuthenticationProvider`, `UserDetailsService` | `AuthorizationManager`, `@PreAuthorize` |
| **주요 기술 및 데이터** | 아이디/비밀번호, OAuth2 SNS 로그인, 생체인식, JWT Access 토큰 발급 | RBAC(역할 기반 권한), ABAC(속성 기반 권한), Scope(OAuth2 범위) |

구현 및 설계 시 단점과 유의할 점

- **토큰 가짜 검증(JWT 탈취 위험)** : 인가 단계에서 매번 DB를 조회하면 성능이 떨어지므로 JWT 토큰 내부에 들어있는 권한(Claims) 정보를 믿고 처리하는 경우가 많습니다. 이때 토큰이 탈취되면 해커가 탈취한 권한을 그대로 행사할 수 있으므로, 토큰 만료 시간을 짧게 가져가고 Refresh 토큰 전략을 함께 써야 합니다.
- **인가 로직의 복잡성 관리** : 권한 규칙이 복잡해질수록 소스코드 곳곳에 권한 체크 로직이 들어가서 유지보수가 어려워집니다. Spring Security의 표현식 언어(SpEL)나 인터셉터 아키텍처를 활용하여 비즈니스 로직과 인가 로직을 최대한 깔끔하게 격리해야 합니다.

### Stateful vs Stateless

**핵심 개념 차이**

- **Stateful (상태 유지)**: 서버가 클라이언트의 이전 상태를 **기억**합니다. (예: 세션 기반 로그인)
- **Stateless (상태 무상태)**: 서버가 클라이언트의 상태를 **저장하지 않습니다**. 모든 요청은 독립적입니다. (예: JWT/토큰 기반 로그인)

**세부 비교**

| **비교 항목** | **Stateful (세션 방식)** | **Stateless (토큰 방식)** |
| --- | --- | --- |
| **상태 저장소** | 서버 메모리 또는 세션 DB (Redis 등) | 클라이언트(브라우저 LocalStorage, Cookie 등) |
| **인증 메커니즘** | 세션 ID를 쿠키에 담아 주고받음 | 암호화된 토큰(JWT)을 헤더에 담아 요청 |
| **서버 확장성** | **낮음** (서버가 늘어나면 세션 동기화 필요) | **높음** (어떤 서버로 요청이 가도 상관없음) |
| **비즈니스 적합도** | 단일 서버, 어드민 페이지, 전통적인 웹 앱 | 마이크로서비스(MSA), 모바일 앱, REST API |

**Stateful 방식의 장점과 단점**

**장점**

- **보안 통제 용도 용이**: 서버가 세션을 들고 있으므로, 해킹이 의심되는 사용자의 세션을 **서버에서 강제로 만료**시킬 수 있습니다.
- **네트워크 대역폭 절약**: 클라이언트는 짧은 `Session ID`만 보내므로 매 요청마다 주고받는 데이터 양이 적습니다.

**단점**

- **서버 확장(Scale-out)의 어려움**: 서버를 3대로 늘렸을 때, 1번 서버에서 로그인한 유저가 2번 서버로 요청을 보내면 로그인이 풀립니다. 이를 해결하기 위해 Sticky Session을 쓰거나 외부 세션 서버(Redis)를 구축해야 하므로 아키텍처가 복잡해집니다.
- **서버 메모리 부담**: 접속자가 많아질수록 서버 메모리(RAM) 사용량이 급증합니다.

**Stateless 방식의 장점과 단점**

**장점**

- **압도적인 확장성**: 서버는 상태를 보관하지 않고, 들어오는 토큰의 위변조 여부만 검증(Verify)합니다. 서버가 100대로 늘어나도 별도의 세션 동기화 없이 요청을 처리할 수 있어 **클라우드(MSA) 환경에 최적화**되어 있습니다.
- **플랫폼 독립성**: 쿠키를 사용하기 어려운 모바일 앱(iOS/Android)이나 타 도메인 간의 API 호출 시에도 토큰 기반 인증은 매끄럽게 작동합니다.

**단점**

- **토큰 탈취 시 제어 불가능**: 이미 발급된 토큰(JWT)은 만료될 때까지 서버가 강제로 회수하거나 무효화하기 어렵습니다.
- **데이터 무거움**: 토큰 내부(Payload)에 사용자 정보, 권한 등을 담다 보니 요청을 보낼 때마다 네트워크 트래픽을 더 많이 소모합니다.
